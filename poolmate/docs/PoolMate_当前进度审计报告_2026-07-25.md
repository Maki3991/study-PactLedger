## 1. 执行摘要

### 1.1 总结论

独立 PoolMate 已完成一个质量较高、边界清晰的 **Human Present + sponsored Mock 支付编排 MVP**。当前可信能力包括：Telegram 拼单命令与草稿、份额认领、不可变 Checkout、组件级精确分摊、逐人确认、确认失效、稳定支付请求、幂等防重、单进程持久化恢复、本地 Mock Policy/Receipt，以及对应的 React 确认页和管理页。

当前实现特别值得肯定的部分是：资金动作没有伪装成真实链上支付；Mock 成功只进入 `DEMO_CONFIRMED`；Mock Receipt 不返回交易哈希或 Explorer；远程恢复只查询原 operation，不重新发起付款；Checkout 变更会使旧分摊和确认失效。这些约束使本地演示具有可审计性。

但 PoolMate **尚未完成完整产品闭环**。独立应用当前没有真实成员出资、远程 PactLedger 支付基座联调、Injective Testnet/Live 结算、A2A transport、AP2 Mandate/Verifier、履约、个人账单、群总账或多实例恢复证据。产品定义和用户流程中的多个目标态步骤不能作为当前能力声明。

最准确的当前状态是：

> PoolMate 已完成独立的、本地受控的 Telegram 拼单与 sponsored Mock 支付编排 MVP；外部协议、真实资金、链上结算和履约闭环尚未完成。

### 1.2 对外声明门

在获得对应证据前，不得宣称：

- PoolMate 已接入 A2A；
- PoolMate 已符合或已验证 AP2；
- PoolMate 已接通 PactLedger 远程支付基座；
- PoolMate 已在 Injective Testnet 或 Live 完成付款；
- 群成员已经真实出资或完成资金预留；
- 订单已经链上确认、商户已收款或履约完成；
- 当前测试已证明生产环境、真实 Telegram、跨实例或外部网络行为。

### 2.3 资金动作审计原则

PactLedger 的资金不变量是：

```text
Intent -> PolicyDecision -> Approval(optional) -> Settlement -> Receipt
```

独立 PoolMate 当前只在本地 Mock 路径中形成对应的模拟证据链：

```text
PoolMatePaymentRequest
-> persisted Mock PolicyDecision
-> all-participant confirmation prerequisite
-> no-money Mock settlement
-> persisted Mock Receipt
-> DEMO_CONFIRMED
```

这可以证明本地编排和证据隔离，但不能证明 PactLedger 通用资金内核、真实账户/预算/Reservation、Injective 广播或链上 Receipt 已接通。

## 4. 产品流程逐阶段对照

### 4.1 阶段 A：创建草稿

**状态：已实现并验证。**

当前 Bot 支持命令式创建；可选 LLM 草稿提取器默认关闭。LLM 开启时要求完整的 HTTPS base URL、服务端 API key 和 model，并通过 strict structured output 把模型权限限制为草稿标题与目标份额，不能由模型决定商户、价格、收款方、确认、支付或订单状态。

缺少的外部证据：真实 Telegram 群聊触发和真实模型服务调用。

### 4.2 阶段 B：发布与份额认领

**状态：已实现并验证。**

当前流程覆盖：

- `DRAFT -> COLLECTING`；
- 参与人加入、认领、调整和退出；
- 目标份额达到后锁定认领；
- Checkout 确认开始后禁止继续修改份额；
- owner/admin 可以安全取消；
- 取消证据 append-only，付款 claim 有竞态保护。

参与人没有一套独立的完整业务状态机，主要通过 allocation 和 confirmation 状态间接表达。这不阻塞当前 MVP，但与产品文档中更丰富的参与人状态设计不完全一致。

### 4.3 阶段 C：请求最终报价

**状态：已实现但仅本地 Mock。**

代码通过固定 `MockMerchantAdapter` 生成最终报价，owner 需要使用 `/pool_quote` 或按钮手工触发。当前没有：

- 自动请求最终报价的调度；
- Merchant Directory；
- 多商户能力发现；
- Merchant Agent Card；
- A2A Merchant Task；
- 商户签名 Checkout。

因此，流程文档中“PoolMate 自动通过 A2A 请求 Merchant Agent 最终报价”的描述属于目标态。

### 4.4 阶段 D：Checkout 与精确分摊

**状态：已实现并验证。**

当前实现形成不可变 Checkout snapshot，并持久化：

- Checkout ID、version、canonical hash 和过期时间；
- merchant/payee；
- item、quantity 和 unit atomic amount；
- goods、shipping、discount、fee 和 total；
- allocation strategy；
- 每名参与人的组件金额和 total。

金额使用原子单位字符串和 `BigInt` 计算。`BY_QUANTITY` 与 `EQUAL_SPLIT` 均使用稳定的最大余数法分配组件尾差，并校验：

```text
goods + shipping + fee - discount = total
sum(participant component) = checkout component
sum(participant total) = checkout total
```

这是当前独立 PoolMate 最成熟、最可信的业务内核之一。

### 4.5 阶段 E：逐人确认

**状态：已实现并验证。**

每名参与人获得独立确认 token，数据库只保存 token hash；确认页展示同一 Checkout 及本人精确金额。提交确认时校验 Telegram WebApp `initData` 的 HMAC、时效和用户 ID，避免仅凭链接代表他人确认。

确认与 Checkout version/hash、参与人和 allocation 绑定。Checkout 变化后，旧确认会被 supersede/invalidated，不能继续用于付款。

当前证据属于 PoolMate-native Human Present confirmation，不能称为 AP2 Mandate 或 AP2 Trusted Surface 兼容证明。

### 4.6 阶段 F：创建并执行付款

**状态：本地 Mock 已实现；真实支付未实现。**

最后一名参与人确认后，系统通过事务性写入创建唯一的：

- Confirmation Set；
- Payment Request；
- operation identity；
- payment projection；
- outbox record。

本地 Mock Payment Base 会执行确定性策略检查并持久化：

- operation；
- request hash 与 canonical request；
- PolicyDecision 及各项 check；
- Mock Receipt。

Mock 成功只进入 `DEMO_CONFIRMED`，其 `transactionHash` 和 `explorerUrl` 必须为空。代码还拒绝把缺少 HTTPS Explorer 或 transaction hash 的非 Mock 结果写成真实确认。

这条路径验证的是“支付前置条件、幂等和证据编排”，不是资金移动。

### 4.7 阶段 G：履约与完成

**状态：未实现。**

产品和用户流程描述了商户接单、发货、收货、完成、个人账单和群总账，但当前代码没有对应的领域对象、状态转换、API、任务或 UI。当前订单即使进入 `DEMO_CONFIRMED`，也不等于履约完成。

3. 没有履约态意味着“付款成功”与“订单完成”之间的业务责任尚未建模。
4. 没有自动 expiry scheduler，过期报价、确认或卡住任务主要依赖调用时校验和人工恢复，不是完整的后台生命周期管理。

## 6. 协议与支付边界审计

### 6.1 PaymentBaseClient 边界

**结论：设计方向正确，远程能力尚未验收。**

独立 PoolMate 把支付限制在 `PaymentBaseClient` 端口后，没有导入 `web/` 内部 Repository、Policy Engine 或 Settlement Adapter。远程实现具有以下保护：

- 仅允许 HTTPS origin；
- 使用服务端 Bearer credential；
- submit 与 recover path 必须显式配置；
- 拒绝 insecure URL、credential URL、路径穿越和危险 path；
- timeout 与外部错误归一化；
- recover 只按原 operation ID 查询，不重新 submit；
- 返回结果必须满足 settlement mode 和 Receipt 字段约束。

但 `PaymentBaseClient` 只是适配边界。没有远端稳定契约、真实鉴权、请求/响应兼容、幂等冲突和恢复联调证据时，不能判定 PactLedger 集成已完成。

### 6.2 A2A

**结论：未实现。**

当前只有 `sourceProtocol: "A2A" | "MOCK"` 这样的 canonical 类型预留。未发现：

- A2A transport 或锁定版本的 schema/SDK；
- Agent Card；
- Task、Message、Artifact；
- A2A authentication/authorization；
- Task persistence、ownership、idempotency 和 recovery；
- Merchant 或 Payment A2A 端到端测试。

枚举值不能作为协议接入证据。

### 6.3 AP2

**结论：未实现。**

当前逐人确认是 PoolMate-native confirmation evidence。独立应用没有 AP2 Mandate、签名、Credential Provider、Verifier、Trust Anchor 或签名 Receipt。因此只能表述为“为未来 AP2 Human Present 保留演进边界”，不能显示 `AP2 Verified` 或声称兼容 AP2。

### 6.4 Injective

**结论：独立 PoolMate 中未实现。**

当前 `poolmate/` 没有直接 Injective SDK 结算实现，也没有已联调的 PactLedger 远程支付接口。没有真实 transaction hash、可打开 Explorer 和已持久化链上 Receipt，所以任何“Injective 已支付”或“链上已确认”均不成立。

### 6.5 真实成员资金

**结论：未实现。**

运行时配置硬编码为 `sponsored_demo`。`prefunded_participants` 只存在于共享类型和 schema 边界，没有：

- participant account；
- funding entry；
- balance；
- reservation；
- capture/release；
- 多人资金与一次商户付款之间的会计映射。

因此，当前“每人应付金额”是确认和分摊事实，不是“每人已经出资”的资金事实。

## 7. 幂等、恢复与数据完整性

### 7.1 已有能力

当前实现对单进程、SQLite 部署场景提供了较扎实的保护：

- Checkout canonical hash 和 version；
- confirmation token hash；
- Confirmation Set 与 Checkout 唯一绑定；
- Payment Request idempotency key；
- operation ID 与 request hash 绑定；
- 相同 operation、不同请求返回冲突；
- outbox claim 和持久化 lease；
- 提交中断后进入 `PAYMENT_UNKNOWN`；
- recover 查询原 operation，不重提；
- Mock operation、decision 和 receipt 持久化；
- 付款状态、projection、outbox 和 Receipt 字段的交叉约束；
- owner/admin 取消的 append-only evidence；
- 关闭订单与付款 claim 的竞态测试。

### 7.2 能力边界

这些保证不能外推到以下场景：

- 多 backend replica 同时 claim；
- 网络分区下的分布式 lease；
- 真实链上广播成功但 API 超时；
- 远程服务确认成功但本地 Receipt 落库失败；
- 链上 reorg 或长时间 pending；
- Testnet/Live provider 的最终性差异。

Compose 已明确 SQLite 仅部署单个 backend replica。远程 `recover` 委托给尚未发布的远端契约，当前没有独立的链上 reconciler。

## 8. 安全审计

### 8.1 已有保护

- Telegram WebApp `initData` HMAC、时效和 user ID 校验；
- confirmation token 通过 header 传递，数据库只存 hash；
- 敏感确认接口设置禁止缓存；
- 支付和 LLM credential 只由服务端环境变量读取；
- LLM 和 Payment Base URL 限制为 HTTPS，并拒绝嵌入 credential；
- 远程支付使用 Bearer auth；
- Nginx 模板设置 `nosniff`、`no-referrer` 和 `X-Frame-Options: DENY`；
- Mock Receipt 与真实 Receipt 在 API/UI 中分型；
- 静态扫描未发现对 `web/`、Telegraf、Codex CLI/SDK 或 PTY 的依赖。

### 8.2 待补强项

| 风险 | 当前情况 | 建议 |
|---|---|---|
| 公共确认接口滥用 | 未见显式 rate limiting 或失败次数限制 | 在反向代理和应用层增加基于 IP/token 的速率限制与告警 |
| 管理员鉴权 | 单一静态 API key；前端保存在 `sessionStorage` | 生产环境改为短期会话、角色权限和可撤销凭证；至少限制来源和轮换 key |
| 浏览器安全头 | Nginx 模板没有 CSP 和 HSTS | 在确认实际 TLS 终止位置后增加 CSP、HSTS 和更细的 `Permissions-Policy` |
| 外部服务凭证 | 依赖部署环境正确注入 | 增加 secret manager/部署检查，禁止日志输出 request header 和 token |
| 审计事件 | 有专用证据表，但没有通用 append-only domain/audit ledger | 为状态转换、管理员操作、恢复和外部调用建立统一审计事件 |
| 单实例 SQLite | 适合当前 MVP，不适合横向扩容 | 生产扩展前迁移到支持跨实例事务/锁的数据库与队列 |

## 12. 风险分级

### P0：对外声明和资金真实性

1. **协议误报风险**：A2A、AP2、PactLedger 远程支付和 Injective 均未完成，目标流程文案不得直接作为产品完成声明。
2. **出资误报风险**：当前只有 `sponsored_demo`，参与人的精确分摊与确认不等于真实出资、预留或扣款。
3. **链上误报风险**：没有 transaction hash、Explorer 和持久化链上 Receipt，不得显示“链上已确认”。
4. **闭环误报风险**：没有履约、收货和完成状态，`DEMO_CONFIRMED` 不等于订单完成。
5. **外部契约阻塞**：Testnet/Live 客户端边界存在，但远程稳定支付 API 未发布、未联调。

### P1：产品与工程完整性

1. 最终报价由 owner 手工触发，不是自动 Merchant Task。
2. 固定 Mock Merchant/payee/asset，不是 Merchant Directory 或通用商户能力。
3. 无真实 funding ledger、Reservation、capture/release。
4. 无履约、自动过期、失败复核、个人账单和群总账。
5. 恢复只在单进程 SQLite 范围内有证据，无跨实例和链上 reconciler。
6. 公共确认接口缺少显式 rate limiting；管理员鉴权和浏览器安全头需要生产加固。
7. 目标文档与当前实现混写，验收数字已经漂移。

### P2：可维护性与运营体验

1. 缺少 README、运行手册和故障处置 Runbook。
2. 缺少 OpenAPI、SSE、通用 Job/Audit 页面。
3. 缺少外部依赖的可重复验收脚本和证据归档规范。
4. 测试覆盖以 SQLite、Mock 和 fixture 为主，尚未建立远程 contract test 套件。

### P0：发布并联调稳定 Payment Base 契约

### P1：决定资金模式和完成范围

3. 商户接单、发货、收货、完成；
4. 个人账单和群总账；
5. 通用 audit event 和恢复面板。

### P2：最后接入协议层

A2A 只在存在真实跨 Agent/跨服务协作需要时接入，并必须包含 transport、鉴权、持久化 Task/Artifact、幂等和失败恢复。AP2 必须等待 Mandate、签名、Verifier 和 Receipt 能形成完整互操作证据后再声明。
