## 一、开场 30 秒（第 1 页 · 封面）

**台词：**

> 各位评委好。先问一个问题：今天在场的每一个 Agent 项目，如果明天让 Agent 自己拿着钱去完成任务——**它把钱转错人了，谁负责？**
>
> 我们是 PactLedger，Agent 的资金控制层。一句话说清楚我们做什么：**Agent 可以提出花钱，但只有规则能决定放行。**
>
> 接下来五分钟，我会用两个真实跑着的应用证明这件事，并且告诉大家，为什么 Agent 的支付必须发生在 Injective 上。

**要点：** 开场不要寒暄团队介绍。直接把"钱"和"责任"砸出来。全场安静后再报名字。

## 二、问题（第 2 页 · 约 30 秒）

**台词：**

> Agent 正在从"回答问题"变成"替人办事"。它自己拆任务、选服务、调别的 Agent、付商户。这一轮任务可能产生几十次支付。
>
> 于是我们有了四个今天没人回答的问题：它能花多少钱？能付给谁？哪些动作必须人来批？出了错怎么追责？

**要点：** 四个格子逐个指过去，语速放慢。"幻觉=转账"是全场第一个记忆点，说完停顿一拍。

## 三、机会（第 3 页 · 约 25 秒）

**台词：**

> 看一下现有工具各自解决了什么：钱包解决签名，支付网关解决通道，工作流平台解决任务编排。**都是好工具，但没有一个是"财务制度"。**
>
> PactLedger 补的就是这层——一个 Agent 在什么条件下可以代表用户、团队、甚至另一个 Agent 花钱，并且每一次放行和拒绝都留下证据。
>
> 一句话定位：**PactLedger 是 Agent 的可编程财务控制层。** Agent 只能提交花钱意图，剩下的全部由基座接管。

【可砍】三个已有工具的对比缩减为一句："钱包、网关、工作流都不是财务制度"。

## 四、产品定义（第 4 页 · 反色页 · 约 40 秒）

**台词：**

> 这是我们的核心设计，请记住这条链：**Intent → Policy → Approval → Settlement → Receipt。**
>
> Agent 提交的永远只是一个结构化意图：谁付给谁、多少钱、什么用途、有效期到什么时候。然后 Policy Engine 逐项检查——预算够不够、收款方在不在白名单、用途合不合法。超阈值的动作必须等人点批准。**全部通过之后，钱才会进入结算层，最后留下一张可验证的回执。**
>
> 三个设计细节，是我们和很多"加个转账按钮"项目的区别：第一，Policy 返回的不是一个布尔值，而是每一项检查的理由；第二，**被拒绝的请求也会入账**，它是证据而不是异常；第三，这条链对任何业务都一样。

**要点：** 这一页是全场技术核心，必须讲慢。手指沿着五个节点划过去。

【不可砍】这页永远不能砍。

## 五、铁律（第 5 页 · 约 30 秒）

**台词：**

> 左边是今天大多数 Agent 应用的做法：Agent 直接拿着钱包 API 或者私钥。Prompt 注入、模型幻觉、一句社会工程学——任何一环出错，钱就没了，而且连复盘的材料都没有。
>
> 右边是我们：业务 Agent **在架构上就碰不到结算层**。结算适配器只认 Policy Engine 的放行决定，没有第二个入口。
>
> 所以我们从不要求用户"相信我们的 Agent 永远正确"。我们的承诺反过来的：**即使 Agent 犯错、被骗、被注入，它也越不了权。**

**要点：** "即使犯错也越不了权"是第二个记忆点，放慢、加重。

**台词：**

## 九、Injective 的作用（第 9 + 10 页 · 约 60 秒 · 重点章节）

> ⚠️ 评委如果是 Injective 赛道评审，这两页是打分页。务必脱稿、直视、讲满。

**第 9 页台词：**

> 现在回答那个问题：钱最后在哪结？为什么必须是 Injective？
>
> 在我们的架构里，分工非常清楚：**Policy 决定能不能付，Injective 证明真的付了。** 区块链对我们不是页脚上的技术标签，而是审计证据的生产者。被批准的 Agent 服务费和商户付款进入 Injective 结算适配器，交易哈希、区块高度、持久化 Receipt 三样东西，任何人都可以在 Explorer 上点开验证。
>
> 为什么是 Injective 而不是别的链？四个数字：亚秒级出块——Agent 不用为几分钱的服务费等半分钟；接近零 Gas——微支付在经济上成立的前提；L1 原生金融结算层——证据即交易本身；7×24——机器经济从不下班。

**第 10 页台词：**

> 再往深说一层。Agent 经济是**高频微支付经济**：一个 Agent 一轮任务可能买几十次研究、回测、风控服务，单笔常常只有几美分。
>
> 传统收单 2–3% 费率加 T+1 结算，微支付直接被手续费吃掉；以太坊主网一笔 Gas 好几美元，手续费比支付额还高。**Agent 之间的按次付费，在这两条轨道上根本不存在经济可行性。** 在 Injective 上，一笔 Agent 服务费的成本约等于一次 API 调用——这门生意第一次成立了。
>
> 我们的路线也很清楚：今天，Testnet 上的 MsgSend 结算，Receipt 落库可验；明天，Treasury 合约把白名单、额度、防重放**直接锁进链上**——控制层和结算层在同一条链上汇合。Injective 对我们来说不是接入口，是长期结算底座。

**口径 A（真实 Testnet 交易已跑通）—— 加讲：**

> 就在这次黑客松期间，我们已经完成了真实结算：这是一笔 KaleidoX 风控服务费的 Testnet 交易，交易哈希在这里，Explorer 链接我现场点开——（打开 Explorer）——区块高度、时间戳都在。同一笔 Intent 您让我重试一百次，它只会返回同一张 Receipt，不会重复付款。

**口径 B（尚未跑通）—— 加讲：**

> 如实向各位汇报当前状态：Injective 官方 SDK 的 Testnet 适配器已经完成并通过单元测试——收款白名单、denom 精度、原子金额、错误码全部就绪；当前只差钱包与测试币配置。我们在页面上也如实标注了 Mock 与 Testnet 的区别——**各位今天看过很多"链上已确认"的页面，我们的原则是：没有可打开的 Explorer，就绝不写"已确认"。**（顺势接到第 12 页）

## 十四、评委 Q&A 预案

**Q1：这和"给 Agent 一个带限额的钱包"有什么区别？**
> 限额只是 Policy 十几项检查里的一项。我们有用途校验、收款方白名单、有效期、人工审批阈值、协议标签，且每一次决策都产出结构化理由并入账。钱包是签名工具，我们是决策与证据系统——而且业务 Agent 在架构上接触不到签名。

**Q2：Policy Engine 本身被绕过/被攻破怎么办？**
> 两层回答：今天，结算适配器只接受 Policy 服务侧的放行决定，私钥只存在于服务端，应用层没有第二条路；明天，Treasury 合约把白名单、额度、防重放锁进链上，即使服务端被攻破，合约层也不认越权交易。

**Q3：为什么一定要用链？中心化账本不行吗？**
> 中心化账本解决"记录"，链解决"任何人可独立验证"。Agent 经济的参与者互不信任——买方 Agent、卖方 Agent、平台、用户——交易哈希和区块高度是中立第三方证据。并且只有 Injective 的亚秒确认和近零成本让高频微支付成立（展开第 10 页四个数字）。

**Q4：Injective 在你们系统里是刚需还是噱头？**
> 刚需。我们的演示里每一笔 Agent 服务费、每一笔商户付款都走 Injective 结算适配器，Receipt 的哈希、高度、Explorer 链接全部来自 Injective。您可以现在随便挑一张 Receipt，我们当场在 Explorer 打开它。（口径 B 时补充：适配器已完成并测试，配置钱包后立即切换，切换成本是一行环境变量——这正是适配器模式的意义。）

**Q5：你们是不是在 Injective 上交易 A 股？**
> 不是，这是一个我们刻意守住的边界。股票研究是业务动作，Agent 支付是资金动作，两个领域对象严格分开。PandaAI 负责数据与解释，Injective 负责 Agent 服务费和商户付款的结算与回执。把股票订单伪装成链上订单，反而是不诚实的设计。

**Q6：多 Agent 互相支付的市场什么时候成立？**
> 今天 KaleidoX 内部已经在发生：Strategy Agent 向 Research、Backtest、Risk Agent 按次采购服务，这就是微型的 Agent-to-Agent 市场。我们和外部平台之间用标准 A2A Agent Card 打通，任何平台 Agent 都可以向我们提交任务并触发同一套 Intent→Receipt 流程。

**Q7：人工审批会不会成为瓶颈？**
> 审批是按阈值触发的：小额、白名单内、用途合法的支付全自动；只有超限或高风险动作才进入人工队列。这正是"分级信任"，和企业财务制度同构。

**Q8：被拒绝的请求为什么要入账？**
> 因为拒绝是最有价值的安全证据。一次"把钱转给我"的拒绝记录，证明规则在工作；长期看，拒绝模式就是 Agent 行为的风控与信誉数据。

**Q9：团队是怎么分工 / 怎么在黑客松完成这么多工程的？**
> 我们把领域边界画得极窄：基座只管五个金融原语，业务语义全部在应用层。这个约束让多个人（和多个编程 Agent）可以并行工作而不打架。42/42、100/100、29/29 的测试数字就是这么守住的。

**Q10：比赛结束后第一件事做什么？**
> Treasury 合约——把白名单、单笔上限、防重放从服务端策略升级为链上强制；然后是 x402/ACP/AP2 协议连接器，把外部支付协议归一到同一个 Intent 模型。赛道层面，先把 PoolMate 的 Telegram 生产联调和 iMessage 接入做完。
